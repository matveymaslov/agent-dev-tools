# agent-rules-gen

Keep project rules in one Markdown source. Generate `AGENTS.md` and `CLAUDE.md`
with the right sections for each agent, and catch drift before it reaches a commit.
Zero dependencies. Node.js 22 or newer. MIT licensed.

## Install and try

Run it from a checkout of this repository, or copy this folder into your project as
`tools/agent-rules-gen`. No installation or build step is needed:

```sh
node tools/agent-rules-gen/bin/agent-rules-gen.js generate --source rules.md
node tools/agent-rules-gen/bin/agent-rules-gen.js check --source rules.md
```

To try the bundled example from this tool's directory:

```sh
node bin/agent-rules-gen.js generate --source examples/rules.md --out-dir demo
node bin/agent-rules-gen.js check --source examples/rules.md --out-dir demo
```

This creates `demo/AGENTS.md` and `demo/CLAUDE.md`. Running `generate` again leaves
their bytes and modification times unchanged.

For a local npm installation, run `npm pack` in this directory, then run
`npm install --save-dev /path/to/agent-rules-gen-0.1.0.tgz` in the consuming project.
The installed executable is `agent-rules-gen`; package imports resolve to the library.
Use a checkout or a packed tarball as above; check `npm view agent-rules-gen`
yourself before assuming a registry release exists.

## Source format

Every section starts with its own metadata header. This is a deliberately small
subset of YAML-style front matter, parsed without a YAML dependency:

```markdown
---
agents: [codex, claude]
claude: |
  ## Changes
  Keep patches focused and explain their effect.
---
## Changes
Keep patches focused. Summarize their effect when finished.

---
agents: [codex]
---
## Verification
Run the relevant tests before reporting a change as complete.
```

| Field | Meaning |
| --- | --- |
| `agents: [codex]` | Include in `AGENTS.md`, also usable by other readers of that file. |
| `agents: [claude]` | Include in `CLAUDE.md`. |
| `agents: [codex, claude]` | Include in both files. Order does not change output order. |
| `codex: \|` or `claude: \|` | Optional replacement for that agent's entire section body, including headings. |

Indent every nonempty override line with **two spaces**; deeper indentation is
preserved. An override must target a listed agent and cannot be empty. The normal
Markdown body may be empty only when every selected agent has an override.
Unknown fields, duplicate fields/agents and malformed headers are errors.
Unmarked introductory prose is an error; put shared introductions in a section.

Sections retain source order. Markdown is literal, including internal blank
lines and trailing spaces used for hard breaks. Blank boundary lines are removed.
A column-zero `---` outside a fenced code block begins the next section; use `***`
for a body horizontal rule. Backtick and tilde fences must be closed, in section
bodies and in wording overrides alike. Full YAML
(quoted keys, aliases, nested mappings, folded scalars) is intentionally unsupported.

## Generated blocks and manual text

Each output contains exactly one block bounded by these reserved lines:

```markdown
<!-- agent-rules-gen:begin -->
<!-- Generated by agent-rules-gen. Do not edit this block.
Source: "rules.md"
Source SHA-256 (UTF-8, LF, no BOM): <64 hexadecimal characters>
Target: codex
-->

...selected rules...

<!-- agent-rules-gen:end -->
```

The header identifies the source relative to the output directory (absolute when
Windows paths are on different drives). The hash covers
the **whole source**, with CRLF converted to LF and an optional UTF-8 BOM removed.
Even an edit to a section used only by one agent marks both headers stale. No
timestamp is embedded, and displayed path separators are always `/`.

For existing files without markers, `generate` appends a block. Otherwise it
replaces only the bytes from the begin marker through the end marker. All text
outside those boundaries, including BOM, whitespace and the final newline, is
preserved. Review and remove duplicated old manual rules yourself after migration.
Broken, reversed, inline or duplicate markers cause an error before either file
is written. The `<!-- agent-rules-gen` prefix is reserved in both source and output.

Marker text that is **quoted inside a fenced code block** (backtick or tilde
fence) in your own text is documentation, not a marker, and is ignored. That is
how a README or contributor guide can show the markers without confusing the
tool:

````markdown
```markdown
<!-- agent-rules-gen:begin -->
...
<!-- agent-rules-gen:end -->
```
````

Only fenced blocks are skipped. A marker quoted inline in a prose line, or in an
indented code block, still counts as a marker (or as a malformed one) and is an
error. A code fence that is never closed anywhere in a destination file is also
an error, because the tool cannot tell which later lines are quoted; close the
fence and run again.

`check` compares the complete expected block, not just the header hash. Edited
rules, edited headers, missing files/blocks and stale source all fail. It never
creates or updates files. `generate` repairs edited blocks from the source, so
move any intentional edit into the source before regenerating.

## CLI, CI and pre-commit

```text
agent-rules-gen <generate|check> [--source rules.md] [--out-dir .]
```

Paths resolve from the current working directory; source paths do not resolve
from `--out-dir`. Quote paths with spaces. Use `--help` for usage.

| Exit | Meaning |
| --- | --- |
| 0 | Generated successfully, or check is fresh. |
| 1 | Check found missing, stale, edited or unsafe output. |
| 2 | Invalid arguments/source, unreadable source or a generation I/O error. |

Commit the source and both generated outputs. After checkout, run this command
in CI (no Git diff, shell utilities or dependency installation needed):

```sh
node tools/agent-rules-gen/bin/agent-rules-gen.js check --source rules.md
```

For a pre-commit hook, add this command to your existing hook. If creating a new
`.git/hooks/pre-commit`, use the following content with LF line endings:

```sh
#!/bin/sh
exec node tools/agent-rules-gen/bin/agent-rules-gen.js check --source rules.md
```

Make the hook executable on Linux (`chmod +x .git/hooks/pre-commit`). Git for
Windows supplies the shell for Git hooks; Node must be on PATH. Merge this into
any existing hook instead of replacing it. The tool does not install hooks or
change Git configuration. A hook checks the **working tree**, not the Git index;
partial staging can still produce an inconsistent commit, so also check in CI.

## Library

```js
import { readFileSync } from 'node:fs';
import { parseRules, renderRules, generate, check } from 'agent-rules-gen';
// For a copied checkout: import from './tools/agent-rules-gen/lib/index.js'.

const source = readFileSync('rules.md', 'utf8');
const sections = parseRules(source); // [{ agents, wording, body }]
const blocks = renderRules(source, { sourceName: 'rules.md', eol: '\n' });
console.log(blocks['AGENTS.md']); // block only, no final newline

const { changed } = generate({ source: 'rules.md', outDir: '.', cwd: process.cwd() });
const { ok, issues } = check({ source: 'rules.md' });
// changed: absolute paths; issues: [{ file: absolutePath, reason: string }]
```

All functions are synchronous. Invalid source/options throw. `check` reports
destination problems as issues; `generate` throws on unsafe destinations or I/O
errors. `generate` also returns `ok: true` when it succeeds. Both filesystem
functions default to `rules.md` and the current directory. `renderRules` defaults
to LF; its `eol` option accepts only `\n` or `\r\n`.

## Portability and limits

- UTF-8 only, optionally with BOM. Invalid UTF-8 is rejected before writing.
- New files inherit the source's first newline style. Existing blocks keep their
  first newline style; when appending, the file's first newline wins. Otherwise
  the source style is used. Mixed newlines in unmanaged text are untouched.
- Hash normalization keeps checks stable across Git LF/CRLF checkout conversion.
  Normalizing a whole generated block's line endings is allowed; content edits
  are not. Lone carriage returns in the source are rejected.
- Only the two fixed outputs and one source are supported. Even an agent with no
  selected sections gets an empty generated block, removing previously generated
  rules for that agent. There are no plugins, includes, template execution or Git
  subprocesses. The npm package has no runtime or development dependencies.
- Destination symlinks and nonregular files are refused. Both destinations are
  validated before writes. Replacement uses a temporary file in the same directory
  and rename, preserving existing permission bits on POSIX.
- Each replacement is atomic, but the two files are not a transaction. A disk
  failure between renames can leave one stale file; fix the I/O issue and regenerate.
  Use a single writer and do not edit files concurrently with generation.
- Source metadata and markers are a format contract, not a security boundary.
  This tool does not decide whether a rule is safe or enforce agent behavior.

## Development

```sh
npm test
```

`npm test` runs `node --test "test/*.test.js"`; the package `exports` field
selects `lib/index.js` for consumers. Tests use the built-in
[Node test runner](https://nodejs.org/api/test.html). They exercise the real
parser, filesystem and CLI, with no test dependencies. Temporary fixtures are
removed individually; if the OS temp directory is read-only, tests use a
temporary directory here instead.

The repository's root workflow runs these tests on Linux and Windows with Node 22
and 24. Run `npm pack --dry-run` to inspect the package contents.
